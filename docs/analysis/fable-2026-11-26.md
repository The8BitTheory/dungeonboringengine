# Independent analysis: performance, size, tests (vdc-basic, dungeonboringengine, Crawl 128)

As of: 2026-11-26. Revisions examined: `vdc-basic` branch `v3` (`6d2afe3`), `dungeonboringengine` branch `step2/textures-0.2` (`1c4aaed`), `dungeoncrawlerjam2025` branch `dbe-0.2` (`4f5ec39`). No production code was changed and nothing was committed. Only this file is new; measurement logs are in `build/fable/` (not versioned).

Labeling of the numbers:

- **measured (source)**: from a spec, a result file or a run of this analysis.
- **derived**: computed from measured numbers (difference, share). The calculation is given.
- **estimated**: not measured.

Unit "µs" for VICE: The monitor's stopwatch counts 1 MHz cycles even with FAST (985 248 per second, measured, P7 12.4). One stopwatch cycle is therefore about 1 µs of real time.

## 0. Summary

1. **Half of Crawl's frame time is in the game's BASIC, not in the engine or VDC-BASIC.** Compiled at 2 MHz in VICE: BASIC ≈ 57 %, VCL ≈ 38 %, `VIEW` ≈ 5 % (derived from the per-key breakdown, section 1.1). This breakdown exists only unversioned in `dungeoncrawlerjam2025/build/why/` and is in no spec.
2. **`VIEW` is exhausted for Crawl.** Even −20 % `VIEW` would be −1 % frame time. M1/M2 (P6k) could at best have brought −0.5 % by calculation; measured were −0.1 % / −0.5 %. This could have been read off existing numbers before the implementation.
3. **Largest single lever: the ghost AI in `crawl.bas` (lines 7800–8020).** It costs about 45–48 ms per frame, around 30 % (derived). The cause is float divisions in `FNPX`/`FNPY`/`FNFD`. That is more than everything P6i, P6j, P6k and P2f brought together.
4. **Size:** VDC-BASIC has no space problem. The limit `$2F00` is only the address of the test helper `zvt`; up to `$4000` there are 4 374 bytes free. The engine's lib, in contrast, is full (code 14, LIBTAB 49, LIBBSS 39 bytes free, measured). Low-risk options are +512 bytes of code by moving tables to bank 0 `$0E00–$0FFF`, or +1 KB through `LIB = $AC00`.
5. **Tests:** The reference chain is good (independent reference, second painter, external comparison with 1.0f, control probes). The offline tests are cheap (about 2 minutes together, measured). Gaps: not a single value from real hardware, no image comparison in Z64K for engine and game, no NMI test, several measurement and diff tools exist only in `build/`.

## 1. Performance

### 1.1 Where the time per frame goes (Crawl 1.1, compiled, 2 MHz, VICE)

Source: `dungeoncrawlerjam2025/build/why/e1_110/ev.json` and `e1_100f/ev.json` (experiment `exp1.py` of 2026-11-26 07:23, state "1.1 P6i", i.e. before P6j and P2f). Breakpoints at the stub entry and exit as well as at entry and end of `VCL`. The stopwatch starts when the key is fed in. The sum over 39 keys is 3 415 965 and matches the recorded value 3 411 580 (`timing-results.json`, "1.1 P6i").

Of the 39 keys of the walkthrough only **20** draw a frame. The other 19 are wall bumps with 5 872–8 291 µs per key, 124 115 µs together (measured). Mean over the 20 frames (measured, evaluation of this analysis):

| small engine calls (`SETPOS`, `SETITEM` …) | 306 | 0.2 % | 60 |
| `VIEW` with stub | 8 286 | 5.0 % | 8 499 |

| **Frame total** | **164 592** | | 162 877 |

State today (P2f), derived from the recorded sums:

- P6i → P6j: −58 188 over the walkthrough, i.e. −2.9 ms per frame.
- P6j → P2f: −248 682, i.e. −12.4 ms per frame. That is almost entirely `VCL`.
- Frame today ≈ (3 104 710 − 124 115) / 20 = **149 ms**. Of this **BASIC ≈ 84–86 ms (≈ 57 %)**, **VCL ≈ 55–57 ms (≈ 38 %)**, **`VIEW` ≈ 8 ms (≈ 5 %)**.

Further configurations:

- **Z64K, compiled, 2 MHz:** 230 jiffies = 3.82 s versus VICE 3.15 s (measured, `timing-results.json`). The difference of 0.67 s falls on the 20 frames, i.e. ≈ +33 ms per frame due to VDC wait times that VICE does not model (derived). Frame ≈ 183 ms: VCL ≈ 90 ms (≈ 49 %), BASIC ≈ 85 ms (≈ 46 %), `VIEW` ≈ 8 ms (≈ 4 %).
- **Interpreted, 2 MHz:** sum 21 652 569 (measured). The wall bumps cost 99–124 ms per key (measured, `build/timing/timing.json`). A frame thus needs ≈ 980 ms, of which ≈ 93 % is BASIC (derived).
- **Demo (Westwood 140 × 96), VICE interpreted, 2 MHz:** `VIEW` 22 975, VCL 98 761 per frame (measured, P6 "Result P6l", tour with 74 keys). `VIEW` there is 19 % of `VIEW` + VCL. The BASIC share of the demo is not measured.

Composition of the VCL list in Crawl (measured, list dumps `build/why/e1_110/k*_b0.bin`, 20 frames): on average **6.2 entries, 505 lines (max. 689), 6 557 bytes**. Only VMC type 2 and VMF type 5 occur. The frames consist of vertical stripes of 5–50 bytes width and 96 lines height. VCL time in Crawl therefore depends on the line count: 69 198 / 505 ≈ 137 µs per line before P2f (derived). The fixed cost per entry (P6g: 650–690 cycles) does not matter with 6 entries.

What the BASIC is stuck on (derived): On a turn (`E`/`Q`) the program reaches the `SETPOS` call 54.5–56.1 ms after the key. A wall bump that only passes through the key dispatcher costs 5.9 ms. In between lie `GOSUB 7800` (ghost AI) and two `POKE`s. The ghost AI therefore costs about **45–48 ms per frame, even on every turn**. It calls `FNPX`/`FNPY` about eight times (one float division, `INT` each, plus a multiplication for `FNPX`), `FNPG` and `FNPD` three times and `FNFD` once. Between `SETPOS` and `VIEW` there are a further ≈ 4.7 ms for six `POKE`s with expressions (measured: distance between the two stub calls).

VDC wait times: In VICE almost nothing (coarse busy model, P6g 4.4). In Z64K ≈ 33 ms per Crawl frame (derived, above). In chunky mode the VDC has only about 16 free memory cycles per character line during display; a copy of 8 bytes needs 148–244 µs there (measured in Z64K, P2g 4.2). **There is not a single value from real hardware.**

For comparison the forecasts that were right: `byte_edges` −18 % estimated, −16.5 % measured (P6h); the VCL additional costs in P6i and P6l. There it was only counted how many operations with **measured** unit costs are dropped or added.

Pattern:

1. **No budget from above.** The local gain was not multiplied by the share of the frame. M1 would have brought only 10.6 % × 5 % ≈ 0.5 % even with the full forecast.
2. **Speed of new code from instruction or register counting.** These estimates were off by a factor of 1.7 to 3 because fixed portions (waits, prologue, table accesses) were missing.
3. **Space gain without counter-calculation.** The removed code was counted, the new code estimated.
4. **Measurement on a different configuration than the target.** Bench in bitmap mode instead of chunky (P6g 4.4), demo map instead of Crawl, 39 keys instead of 20 frames, assumptions about geometry without looking at the test geometries.
5. **Emulator as the yardstick.** VICE models the VDC coarsely, Z64K is a model read from bytecode. Every VDC-bound forecast is provisional until a hardware run.

Rule of thumb from this: Forecasts of the form "n operations fewer × measured unit cost" are reliable to ±10 %. Forecasts of the form "the new code needs only x cycles" are not; halve the savings here or measure beforehand.

Consequence of the breakdown from section 1 for the lib: From now on it should be optimized **for size instead of cycles**. `VIEW` is 5 % of the Crawl frame; trading cycles for bytes costs almost nothing.

### 2.3 Architecture decisions that permanently cost space

1. **Lib in the fixed 11 KB window under I/O**, squeezed between wall DTS and LIBTAB, with three separate limits (code, LIBTAB, BSS).
2. **Uneven distribution:** Bank 0 `$1C00–$3FFF` (9 KB) is reserved for VDC-BASIC, of which 4.4 KB are free. At the same time the lib is missing 14 bytes.
3. **Setup and validation on the C128 instead of in the tool:** format check, cell table (`gcells`), tile tables (`mtiles`, 768 bytes BSS for `tpl`/`tph`/`tsm`). That is 22 % of the code for work that runs once per level and that the tools already check.
4. **Generality at runtime:** style resolution per wall in every `VIEW` (`resolve`, `gsetx`), interval lists for arbitrary geometries, clipping of arbitrary sprites. Crawl uses little of this but pays the space. This also explains 1 337 instead of 420 cycles per wall (measured, P6k 2.2).
5. **Overflow handling with count mode** (`iovf`, `E_TOOMANY`, `E_PARTIAL`) instead of a budget check in the tool (`dbeview.budget` already exists).
6. **Two output paths for VMS lists** (type 9 from bank 1, type 12 clipped in the buffer, plus the dead switch `VMS_COPY`).
7. **VDC-BASIC as one binary** with parser, drawing commands and RXV. As long as `$4000` is the limit, this costs nothing; conditional assembly is not worthwhile.

## 3. Test quality and focus

### 3.1 Significance

Strengths:

- **Independent reference:** `dbeview.view` was written from the spec before the 6502 version; comparison is byte-exact (sim65).
- **Second, differently built probe:** `paint_reference` paints without coverage and spans and checks the pixels.
- **External comparison:** Crawl 1.1 against the real 1.0f (74 prompts, VRAM and registers) and `crawl01` against real 1.0f dumps. This is the only comparison that does not come from the same spec.
- **Control probes:** `--control` (one byte falsified, exactly this frame must be reported), `ZVT_INJECT` (`wrong`/`stray`), comparison over the entire 64 KB VRAM.
- Event-driven, own ports, no fixed wait times.

Weaknesses:

- **Correlated errors:** Reference, painter, VCL interpreter `run_vcl` and 6502 code come from the same spec and the same source. A misunderstanding of the spec stays invisible. For everything Crawl does not use (floor, ceiling, wallpaper, far view, clipping, tiles) there is no external comparison, only visual inspection of the demo.
- **VICE does not test the VDC's busy behavior.** All pixel tests of engine and game (`vice_view`, `vice_demo`, `vice_crawl`) are blind to missing ready waits. Z64K covers this for the VDC-BASIC listings, but `z64k_crawl.py` only measures time. A wrong image in Z64K would go unnoticed.

### 3.3 Expensive without benefit

- **Identical double runs in VICE** for timing (VICE is deterministic): one run is enough.
- **`vice_view.py` with eight runs** (interpreted/compiled × 1/2 MHz × with/without `--fix`) after lib-internal changes. Interpreted and compiled differ by ±100 cycles (P6h); they test the interplay with the runtime, not the lib. For lib changes compiled, 2 MHz, `--fix` (the game's configuration) is sufficient.
- **`VMS_COPY` sets in `run_sim.py`** (P6d and P6e run twice) for a build that can no longer be shipped.
- **Full Z64K suites** (`run.sh -z`: 6.7 min per mode; RXV 1 min 18 s; drawing 3 min 25 s; measured, `test/README.md`) after changes that do not touch VDC accesses. Run the drawing suite only for changes to the drawing commands (already handled that way in P2f).
- **Rebuilding and running the 1.0f reference** in every `vice_crawl.py` run: 1.0f does not change; cache dumps by disk hash (`--reuse` already exists for the comparison).
- **Re-measuring old revisions** (already regulated in `AGENTS.md`).
- **Full implementation before the prototype:** M1/M2 lay between 13:02 (analysis) and 16:42 (rejected), with all tests. That is the most expensive single item of the day and would not have started with the budget calculation from 1.3.

### 3.5 Reducing the run time of agent jobs

1. **Budget line mandatory in the job:** "Affected share of the frame × expected savings = expected gain". Below 2 % of frame time no implementation, at most a prototype.
2. **Write the test selection from 3.4 into the job** (commands and what does not run), instead of letting the agents derive it.
3. **Version the measurement tools** (gap 5): profiler, breakdown per key, line timing, diff test.
4. **One entry script per repo** (`test/quick.sh <area>`) that starts the rows of the matrix in parallel and prints one line per test. The whole engine round already ran in parallel in about 5 minutes (log timestamps 08:40–08:45).
5. **VICE timing without double runs; Z64K only for VDC-related changes**, there with at least 3 runs and a statement of the scatter.
6. **Cache 1.0f reference data** (dumps and timings by disk hash).
7. **Fixed time frame per job with an abort rule** (is in `AGENTS.md`); add: After the prototype the agent reports and waits for approval before touching tests and docs for the full implementation.
8. **Generate figures from the builds** (reserve, sizes), do not maintain by hand in README and specs.

## 4. Recommendations

### Top 5

1. **Ghost AI in `crawl.bas` without float (K1), measure the upper bound first.** Largest single item of the frame (≈ 30 %, derived), smallest effort, no lib space needed, test exists.
2. **Run the existing hardware test disks once on a real C128 (K2).** Every VDC-bound number and the refresh risk at reg 36 = 0 depend on emulator models. Without this run K3 is a risk.
3. **Make the breakdown per frame (BASIC/`VIEW`/VCL) a fixed part of the timing and version the tool.** It would have shown M1/M2 to be ineffective before they began and immediately shows the achievable gain for every future proposal.
4. **Create space before a feature needs it: S1 (move `zvt`) and S2 (tables to `$0E00–$0FFF`, +512 bytes of code); remove `VMS_COPY` (S5).** Optimize the lib for size instead of cycles from now on.
5. **`R-ACt` in VDC-BASIC (K3) after the hardware run**, with the versioned diff test and an image comparison in Z64K. About −6 % in Z64K (derived), benefits every VMC caller.

### Do not do

- **Optimize `VIEW` further for cycles** (M1, M3a/M3b, M4, decision tree): at most 1 % frame time in Crawl, the lib is full.
- **Thin out waits** ("every Nth line", unrolling for it): proven wrong in Z64K.
- **Reg 36 as a speed lever**: 0 and 1 equally fast. Only safety is open; after the hardware run rather 1.
- **Optimize VMS command 1/8 for Crawl**: no caller in the walkthrough. Only with a game that uses them.
- **Shrink VDC-BASIC or assemble conditionally**: 4.3 KB free once `zvt` is moved.
- **New build variants of the lib without need**: every variant doubles test sets.
- **Full implementation before prototype and budget calculation.**
- **Write forecasts from instruction or register counting into specs unchecked**: halve the savings or mark as "unmeasured".
- **Re-measure old revisions, identical VICE double runs, full Z64K suites without VDC relevance.**

## 5. Limits of this analysis

- The breakdown in 1.1 comes from an existing, unversioned experiment (state P6i). The values for P2f are derived from it and from the recorded sums, not newly measured.
- The share of the ghost AI is a difference between two measured key types (turn, wall bump), not a direct measurement. The trial measurement for K1 clarifies this in one to two minutes.
- The demo was not broken down (BASIC share unknown). Statements about the demo rest on P6g, P6h and P6l.
- The sizes of S4, S6 and S7 are label distances of today's code; the replacement code is not counter-calculated (pattern 3 applies here too).
- The run times of the VICE tests are estimated from log timestamps, not measured individually. No emulator ran in this analysis.
- For `run_crawl.py` (3 s) only the absence of a cache in the game was checked, not the completeness of the comparison.
